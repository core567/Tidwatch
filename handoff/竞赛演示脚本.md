# TideWatch 竞赛演示脚本（小程序 + PC + 后端联动）

> 适用：现场答辩 / 评委体验。所有数据来自真实后端与状态机，无前端写死、无伪造接口。
> 演示前请先按「演示前准备」把环境与初始数据就位。

---

## 〇、演示前准备（操作员，约 2 分钟）

1. 启动后端：`cd backend && uvicorn app.main:app --host 127.0.0.1 --port 8000`
2. 启动 PC：`cd frontend && npm run dev`，浏览器打开 PC 端
3. 微信开发者工具打开 `miniprogram/`，确认后端基础地址指向同一服务（`miniprogram/config/env.ts`）
4. 确认有一个「待处理/进行中」的演示任务：
   - 若当前任务都已 APPROVED，在 **PC 巡检中心 → 对 TW-002 派发一条现场任务**（关联事件、指派 reach-c），
     或用接口 `POST /api/inspection-tasks`（reachId=reach-c、eventId=TW-002）。
5. 演示账号：`admin / Admin#2026`（小程序当前默认演示模式，免登录也可操作；登录可展示 JWT 模式）

> 数据来源标识（全程口播要点）：MQTT 模拟观测＝「模拟数据」；官方自动站＝月度快照；
> 现场复测/照片＝「人工测量/人工证据」；恢复评估＝后端规则只读输出。

## 一、3 分钟快速演示脚本（评委快速版）

| # | 端 | 操作 | 预期结果 | 讲解词（精简） |
|---|---|---|---|---|
| 1 | PC | 研判工作台/事件列表，点开 **TW-002** | 看到事件状态、触发指标（水位↑）、影响上中下游三断面 | “系统基于模拟监测自动识别异常并生成事件，全程数据可追溯。” |
| 2 | PC | 巡检中心 → **派发任务**（关联 TW-002、reach-c） | 任务进入待接收 | “一键派发到现场人员手机。” |
| 3 | 小程序 | 「任务」Tab：点该任务 → **接收 → 开始巡检** | 状态：待接收→进行中 | “现场人员在手机上接收并开始执行。” |
| 4 | 小程序 | 现场采集：填**人工复测**（水位/浊度）、观察记录、结论；**现场拍照** | 照片真实上传、显示「已上传」 | “人工复测与现场照片真实上传并绑定提交版本。” |
| 5 | 小程序 | 提交 → 切「事件」Tab 看 TW-002 详情 | 出现「已提交，待 PC 复核」、时间线新增节点 | “提交后事件时间线实时更新。” |
| 6 | PC | 巡检中心 → **退回**，填意见（如“补拍水尺近景”） | 任务回到现场，带退回意见 | “PC 审核不通过，带意见退回。” |
| 7 | 小程序 | 「我的」Tab：被退回任务**置顶** → 进入补拍 → **重新提交 v2** | 版本 v2、意见可见 | “现场按意见补充，版本与审核全程留痕。” |
| 8 | PC | **复核通过** | 任务 APPROVED | “闭环通过。” |
| 9 | 小程序/PC | 事件详情 → **恢复评估**（因子分组）+ **关键进展** | 证据不足/已满足分组清晰；时间线完整 | “恢复判定由 F1–F7 规则输出，证据不足会明确说明，绝不把没证据说成正常。” |
| 10 | PC | 打开事件 **复盘报告/报告页** | 完整复盘：证据、任务、时间线、恢复评估 | “一键形成可追溯的复盘报告。” |

**收尾创新点（15 秒）**：监测—研判—派发—现场—审核—恢复评估全链路打通；
小程序与 PC 共用同一后端状态机；模拟/官方/人工三类数据严格区分；离线不断判、缺测不连线。

## 二、5–8 分钟完整演示脚本（带讲解词）

### 场景 A：异常感知（PC + 小程序监测页）
- **PC**：展示三断面数字孪生 / 监测总览，说明 24h MQTT 模拟观测、官方月度快照分区展示。
- **小程序「监测」Tab**：河流拓扑 A/B/C → 点 **中游 B**：
  - 最后有效观测三指标、链路状态徽标、官方自动站深色快照分区；
  - 趋势图：1h/6h/24h/7d 窗口切换、X 轴真实时间、缺测灰色断开（不插值）、触摸查看数值/时间/来源。
- 讲解词：“手机端不是简化看板，而是现场视角的监测终端：链路中断时明确提示‘离线不等于异常’，趋势缺测绝不画假线。”

### 场景 B：事件与研判（PC 主导）
- 打开 TW-002：触发指标方向幅度、影响断面、状态机（8 态）、规则处置建议（标注“规则生成，非 AI”）。
- 讲解词：“研判动作受状态机约束，建议来自规则引擎并标注来源，避免把模型猜测当结论。”

### 场景 C：派发与现场执行（核心闭环）
1. PC 派发 → 小程序「任务」实时出现（WS 推送，无需手动刷新；演示时也可下拉刷新）。
2. 小程序任务详情：展示六步流程条（派发→接收→执行→提交→复核→完成）、任务要求、建议测量项。
3. **接收 / 开始**。
4. 现场采集：
   - 人工复测：水位、浊度数字键盘，水流 0–3 步进；未测可选原因（安全/设备/天气等），格式校验。
   - 观察记录：可语音（真机插件）或手动输入。
   - 现场照片：**「现场拍照」直接开后置摄像头**、「相册选择」仅相册；最多 6 张，单张状态（上传中/已上传/失败重试）。
   - 提交前完整性清单；防重复提交。
5. 提交后到「事件」Tab 验证时间线。

### 场景 D：审核退回与重提（体现版本留痕）
- PC 退回并填写意见 → 小程序「我的」页被退回任务置顶、红色意见、“去重提”。
- 进入采集页显示“第 2 次提交 v2”，补充后重新提交。
- 任务详情「我的提交记录」展示 v1（退回）/ v2，各自复测值与审核意见。

### 场景 E：通过与恢复评估
- PC 通过 → 小程序状态变“已完成”。
- 事件详情「恢复评估」：
  - 第一层结论（证据是否充分、最近评估时间、关键阻碍条件）；
  - 第二层条件三态分组：未满足 / 待补充证据 / 已满足（严格按后端 passed=true/false/null）；
  - 第三层可折叠：规则版本、依据、数据来源、免责声明。
- 讲解词：“恢复结论只读、不驱动状态；即使事件被人工置为 RECOVERED，证据不足时评估仍如实显示 INSUFFICIENT_EVIDENCE。”

### 场景 F：复盘报告
- PC 生成事件复盘：时间线里程碑（自动聚合上百条盲区/抖动噪声）、证据、任务提交与审核、恢复评估、免责声明。

### 「我的」个人中心（可穿插）
- 身份/演示模式标识、五项工作统计（与待办同源 mine=true）、被退回置顶、最近工作记录、实时通道状态、数据来源帮助、登录/退出（演示模式↔JWT）。

## 三、失败处理与备用方案

| 风险 | 现象 | 备用方案 |
|---|---|---|
| 现场无法启动 MQTT broker/ingestor | 场景控制台注入后观测不新增 | 用库内已有 TW-001/TW-002 与历史观测演示；说明“实时注入需 MQTT 基础设施，复盘用历史数据” |
| 微信工具摄像头不可用 | 拍照无法调起 | 用「相册选择」选预置照片走完整上传；强调真机拍照（真机验收项） |
| 语音插件未配置 | 语音不可用 | 改用手动输入观察记录（已实现降级） |
| 现场无网/弱网 | 请求失败 | 演示顶部红色连接提示条：保留旧数据不清空；恢复后自动补拉 |
| 任务都已完成 | 小程序没有待办 | PC 现场重新派发一条任务（30 秒） |
| 后端未启动 | 全部加载失败 | 先启动后端；小程序显示错误页+重试 |
| 时间不够 | 无法走退回重提 | 直接展示任务详情里已有的 v1/v2 历史版本与审核记录 |

## 五、演示数据与接口事实（已用真实接口核对）
- 事件：TW-001(RECOVERED)、TW-002(INVESTIGATING)，触发 waterLevel，影响 reach-a/b/c
- 任务闭环接口：actions(ACCEPT/START/REJECT/APPROVE)、results（max(version)+1 新建提交）
- 审核字段：`POST /actions` body 用 `comment`（REJECT 必填），不是 reason
- 提交复测 measurements 原样存储；requestReevaluate 为输入信号、不回显
- 复盘：`GET /api/events/{id}/review`；恢复评估：`/recovery-assessment`（F1–F7，passed 三态）
